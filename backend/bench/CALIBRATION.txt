# WHAT THIS FILE DECIDES
#
# The harness is checked against PERFORMANCE_PROFILE.md §6.5: it must fit
# edge_info at k ~ 0.99 and the per-edge enumeration at k ~ 2.012 before
# anything it says about an optimisation may be believed. .github/workflows/
# kernel-bench.yml turns that check into a job failure — but ONLY while the
# shim is the one the check was calibrated against.
#
# The reason is the whole point of the exercise. OPTIMIZATION_PLAN.md §5 sends
# Session 2 to remove that quadratic. The moment it succeeds, `allEdges` stops
# fitting 2.012, and a permanent gate on the exponent would go red forever for
# the best possible reason. So the gate keys on the content hash below: while
# it matches, a disagreement means the HARNESS is wrong (the plan says so in as
# many words) and the job fails. Once it stops matching, the same comparison
# becomes a report of how far the exponent moved, which is the number Session 2
# is actually working for.
#
# WHEN TO UPDATE IT
#
# When the shim changes for a reason that is NOT meant to move these
# exponents — a refactor, an unrelated entry point, a comment — and the
# comparison still agrees. Re-record the hash then, so the gate keeps biting.
# Never update it to silence a disagreement: a disagreement is the instrument
# telling you something, and §9 of the plan is about exactly this temptation.
