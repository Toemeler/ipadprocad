# S12 — Die App spricht Deutsch

**Session 12. Die einzige Session dieser Runde, die absichtlich etwas ändert,
das der Nutzer sieht — und nichts anderes.**

**Ergebnis: 836 Schlüssel, zwei vollständige Sprachen, ein Umschalter im
Menü, vier neue Testdateien mit 28 Prüfungen. Keine Geometrie, kein Solver,
kein gespeicherter Wert, kein Messpunkt angefasst.**

Diese Datei ist auf Deutsch geschrieben, weil das Ergebnis auf Deutsch ist.
Sie steht für sich: jede Entscheidung unten ist ohne Blick in die
Commit-Historie nachvollziehbar.

## 1. Was gebaut wurde

| | |
| --- | --- |
| Schicht | `flutter_localizations` + gen-l10n, ARB in `frontend/lib/l10n/` |
| Vorlage | **`app_de.arb`** — die App ist auf Deutsch geschrieben, `app_en.arb` ist die Übersetzung |
| Schlüssel | 836, davon 19 ICU-Plurale, 108 mit Platzhaltern, 106 mit Zeichenbudget, 117 mit Begründung |
| Generat | `lib/l10n/gen/`, **mitversioniert** |
| Zugang | `L.of(context)` im Widget, `L.current` außerhalb |
| Umschalter | eigener Eintrag im „+“-Menü der Galerie |
| Ablage | `<Dokumente>/.cache/settings.json`, neben `externals.json` |
| Tests | `l10n_completeness_test`, `l10n_length_test`, `l10n_toggle_test`, `l10n_no_hardcoded_test` — zusammen 28 Prüfungen |

### Warum das ARB-Deutsch die Vorlage ist und nicht die Übersetzung

gen-l10n liest **aus der Vorlagendatei** die Platzhaltertypen, die
Plural-Kategorien und die Beschreibungen. Wer Englisch zur Vorlage macht,
bekommt die englische Pluralregel (zwei Formen, `one`/`other`) als Rahmen und
darf Deutsch nur noch hineinfüllen. Das geht hier zufällig gut — Deutsch hat
dieselben zwei Formen —, aber es ist die falsche Richtung: die Sprache, in der
die App geschrieben ist, gehört in die Vorlage, und die Übersetzung folgt.

### Warum das Generat mitversioniert ist

`flutter analyze` und `flutter test` laufen damit auf einem frischen Checkout,
ohne dass jemand vorher `flutter gen-l10n` gedacht haben muss. Der Preis wäre
ein Generat, das gegenüber dem ARB veraltet — deshalb prüft
`l10n_completeness_test` beide Richtungen und lädt beide erzeugten Klassen.

### `L.of(context)` fällt auf `L.current` zurück — mit Absicht

```dart
static AppL10n of(BuildContext c) =>
    Localizations.of<AppL10n>(c, AppL10n) ?? current;
```

Rund hundert bestehende Widget-Tests pumpen ein nacktes
`MaterialApp(home: …)` ohne unser Delegate. Ein Wurf an dieser Stelle hätte
aus einer Lokalisierung hundert unbeteiligte rote Tests gemacht. Der Rückfall
liefert genau das, was die App ohnehin hat: **eine** app-weite Sprache.

`AppState` löst rund 170 Meldungen aus Geschäftslogik aus, die keinen
`BuildContext` hat und keinen bekommen soll. Dort steht `L.current`.

## 2. Der Umschalter

Er sitzt im **„+“-Menü der Galerie** — dem einzigen Menü der App, das der App
und nicht einem Dokument gehört. Zwei Eigenschaften, die keine Kosmetik sind:

* **Er nennt die Sprache, in die er schaltet.** „English“, solange Deutsch
  läuft; „Sprache: Deutsch“, solange Englisch läuft. Ein Eintrag, der die
  *aktuelle* Sprache nennt, liest sich als Statuszeile, und Statuszeilen
  werden angetippt, weil Nutzer erwarten, dass etwas passiert.
* **Erkannt wird er über `kLanguageMenuId`, nie über seinen Titel.** Titel
  wechseln mit der Sprache; Ids nicht.

Er liegt sowohl im echten UIKit-Menü als auch in der Flutter-Ersatzdarstellung
(`showMenu`), sonst wäre er außerhalb von iOS und in der Testsuite nicht
erreichbar.

**Ohne Neustart.** `L.locale` ist ein `ValueNotifier<Locale>`, auf den ein
`ValueListenableBuilder` um `MaterialApp` herum hört. Umschalten heißt: neue
`locale`, `Localizations` lädt das Delegate synchron nach (unser Delegate gibt
ein `SynchronousFuture` zurück), der Baum baut neu — er wird nicht neu
*erzeugt*. Der Test `it applies without a rebuild of the app` prüft genau das,
indem er nach dem Umschalten dasselbe `State`-Objekt wiederfindet: eine
Sprachumschaltung, die den Baum wegwirft, verlöre die offene Skizze, die
Scrollposition und jeden Controller darin.

**Persistenz.** `LocaleStore` schreibt nach `.cache/settings.json`, im selben
Muster wie `externals.json` daneben: synchron, Fehler geloggt und geschluckt.
Eine kaputte Einstellungsdatei kostet die Spracheinstellung und **nicht den
Start** — dafür gibt es zwei Tests.

**Gelesen wird sie in `AppState.init()`, nicht in `main()`.** `init()` wird
bewusst gefeuert und nicht abgewartet, damit das erste Bild nicht auf einen
Plattformkanal wartet. Eine Einstellungsdatei vor `runApp` zu lesen, würde
genau das rückgängig machen — in einer Anwendung, deren Startzeit eine
gemessene Zahl ist. **Der Preis ist ehrlich zu benennen:** ein
englischsprachiger Nutzer sieht beim Start ein Bild lang Deutsch. Ein Bild
gegen eine messbare Startzeitregression ist der billigere Handel.

## 3. Der Sprachstand

Die App war schon vorher an Autodesk Inventor angelehnt — `ribbon.dart` sagt
das selbst („every label is Inventor's own wording, so a user who knows
Inventor finds the method they are looking for by name“). Das Deutsche folgt
derselben Regel und nimmt **Inventors deutsche Oberfläche** als Maßstab, nicht
das Wörterbuch.

| Englisch | Deutsch | warum |
| --- | --- | --- |
| Fillet | **Verrundung** | Inventor DE. Nicht „Filet“ — das ist Fleisch |
| Chamfer | **Fase** | |
| Extrude | **Extrusion** | Inventor DE, Substantiv wie alle Feature-Befehle dort |
| Revolve | **Drehung** | das Feature. Die Ansichtsdrehung heißt „Orbit“ |
| Sweep | **Sweeping** | *Inventor DE lässt es englisch.* Siehe §4 |
| Loft | **Erhebung** | Inventor DE |
| Coil | **Spirale** | Inventor DE |
| Shell | **Wandung** | Inventor DE |
| Draft | **Formschräge** | |
| Hole | **Bohrung** | |
| Pattern | **Anordnung** | Inventor DE. Nicht „Muster“ |
| Constrain | **Abhängigkeit** | siehe §4 — hier steht „Zwangsbedingung“ gegen Inventor |
| Dimension | **Bemaßung** | mit ß: nach langem a steht ß |
| Slot | **Langloch** | |
| Offset | **Versatz** | Inventor DE übersetzt es, anders als AutoCAD |
| Feature | **Element** | Inventor DE nennt ein Feature „Element“ |
| Occurrence | **Exemplar** | Inventor DE für die Kopien einer Anordnung |
| Body | **Körper**, Solid Body **Volumenkörper** | |
| Work plane/axis/point | **Arbeitsebene/-achse/-punkt** | Gruppe: „Arbeitselemente“ |
| Trim / Extend | **Stutzen / Dehnen** | Inventor DE |
| Sketch | **Skizze** (die) | |
| Part | **Bauteil** (das) | daher „Ende **des** Bauteils“ vs. „Ende **der** Skizze“ |
| UCS | **BKS** | Benutzerkoordinatensystem; „UCS“ kennt die deutsche Nutzerbasis nicht |

Grammatik, die Software üblicherweise verliert:

* **Genus stimmt.** *die* Skizze, *das* Bauteil, *der* Körper, *der* Layer,
  *der* Modul (Verzahnung, nicht *das* Modul). Die Meldungen richten Artikel
  und Pronomen danach: „**Seine** {count} Elemente werden entfernt“ bezieht
  sich auf *den* Körper.
* **Fugen-n**: Skizze + Name → Skizze**n**name.
* **Durchkopplung**: X-Achse, DXF-Datei, 2D-Skizze, Freihand-Spline.
* **Anführungszeichen**: „unten-oben“, nicht die englischen “oben-oben”.
* **ß vs. ss**: Bema**ß**ung, gro**ß**, schlie**ß**en; aber Wandstärke.

## 4. Die Ermessensentscheidungen

Jede davon hätte auch anders ausgehen können. Hier steht, warum sie so
ausgegangen ist.

### 4.1 „Sweeping“ statt „Ziehen“ oder „Austragung“

Inventors deutsche Oberfläche lässt *Sweep* als **„Sweeping“** stehen, während
sie *Loft* zu „Erhebung“ und *Coil* zu „Spirale“ übersetzt. Das ist
inkonsistent — und es ist das, was die Nutzerbasis gelernt hat. Der Auftrag
sagt: im Zweifel Inventor. Also „Sweeping“, mitsamt der Inkonsistenz.

### 4.2 „Abhängigkeit“ statt „Zwangsbedingung“

Der Auftrag nennt *Zwangsbedingung* als Begriff, den deutsche Ingenieure
benutzen — was stimmt, im Mehrkörper- und im FEM-Kontext. **Inventors deutsche
CAD-Oberfläche sagt durchgehend „Abhängigkeit“**, und die Regel „im Zweifel
Inventor, weil die Nutzerbasis darauf trainiert ist“ schlägt hier den
allgemeinen Sprachgebrauch. Ribbon-Gruppe „Abhängigkeit“, überbestimmte
Skizze, abhängige Bemaßung (Referenzmaß).

### 4.3 „Layer“ bleibt „Layer“

Nicht „Ebene“ — in 3D ist die Ebene die *Plane*, und dieselbe App hat beides
nebeneinander („Arbeitsebene“ und „Layer 0“). AutoCAD DE und die gesamte
deutsche 2D-Praxis sagen ohnehin Layer. Plural formgleich: *die* Layer.

### 4.4 „Wiederholen“ statt „Wiederherstellen“ für Redo

Inventor DE sagt „Wiederherstellen“ (17 Zeichen). Die Schnellwerkzeugleiste
hat für „Redo“ (4) rund 12 Zeichen Platz. Hier gewinnt die Kürzungsregel gegen
die Inventor-Regel, und „Wiederholen“ (11) ist die Form, die auch Office
benutzt — also nicht erfunden, nur die kürzere von zwei geläufigen.

### 4.5 Die englische Inkonsistenz wird nicht mitübersetzt

Dieselben zwei Kantenmengen heißen im Englischen einmal
*interior*/*exterior* und in der nächsten Meldung *fillet*/*round*. Das
Deutsche erbt das nicht: beide Meldungen sagen **Innenkanten / Außenkanten**.
Das englische Original bleibt unverändert — es zu glätten wäre eine Änderung
am Verhalten für englische Nutzer und gehört nicht in diese Session.

### 4.6 `holeTypeLabel(t).toLowerCase()` war ein Grammatikfehler in Wartestellung

Die Meldung lautete `The ${holeTypeLabel(s.type).toLowerCase()} must be wider…`.
Korrektes Englisch. Im Deutschen falsch, weil Substantive großgeschrieben
werden — „die senkung muss…“. Ein `toLowerCase()` an der Verwendungsstelle ist
eine Annahme über die Sprache, verkleidet als String-Operation. Beide
Schreibungen stehen jetzt als eigene Schlüssel im ARB. Dasselbe gilt für
`verbDelete`/`verbMove`: „Flächen zum **Löschen** wählen“ (substantiviertes
Verb, groß) gegen „Select the faces to **delete**“ (klein).

### 4.7 `part_model.dart` behält seine englischen Namen

`typeLabel`, `holeTypeLabel`, `patternKindLabel`, `faceEditLabel`,
`extentLabel` bleiben, wie sie sind. Die Zuordnung *Domänenwert → Anzeigetext*
liegt in `lib/l10n/cad_terms.dart`. Zwei Gründe:

1. `part_model.dart` ist das Modell, nicht die Oberfläche. Es hat keinen Grund,
   `flutter/widgets.dart` zu importieren.
2. Direkt daneben stehen `patternTypeLabel` und `holeTypeName` — und **die
   gehen in die `.ptp`-Datei**. Der Abstand zwischen „Anzeigetext“ und
   „Dateiformat“ ist in dieser Datei zwei Zeilen groß. Ihn nicht zu verkleinern
   ist der Punkt.

### 4.8 Ein echter Fehler, gefunden beim Umbau

`ribbon.dart` schlug die Flyout-Id einer Zeile über deren **Label** nach:

```dart
flyIds: const {'Axis': 'axis', 'Point': 'point'}
…
flyId: flyIds[rows[i].$2],          // $2 ist das LABEL
```

Das funktioniert genau so lange, wie das Label eine englische
Kompilierzeitkonstante ist. In dem Moment, in dem aus `'Axis'` die `'Achse'`
wird, greift der Nachschlag ins Leere — und der Aufklapp-Pfeil verschwindet
kommentarlos von zwei Schaltflächen, mitsamt den acht bzw. neun Methoden
dahinter. **Kein Absturz, keine Ausnahme, nur zwei Befehle weniger.** Die Id
steht jetzt als viertes Feld in der Zeile selbst. Struktur wird nie über
Anzeigetext geschlüsselt.

### 4.9 „Trennen“ und „Teilen“ sind zwei Befehle, nicht einer

Im Englischen heißen beide **Split**: der 3D-Befehl, der einen Körper an einer
Ebene beschneidet, und der Skizzenbefehl, der eine Kurve an einem Schnittpunkt
zerlegt. Inventor DE hält sie auseinander — **Trennen** (3D) und **Teilen**
(Skizze) —, und diese App zeigt beide im selben Ribbon. Ein einziger deutscher
Begriff hätte zwei verschiedene Befehle gleich benannt, was schlechter wäre als
das englische Original. Zwei Schlüssel: `btnSplit` und `btnSplitCurve`.

Ebenso `Offset`: **Versatz von Ebene** (Arbeitsebene) und **Versatz**
(Parallelkurve in der Skizze) — hier deckt sich das eine Wort, aber die
Schlüssel bleiben getrennt, weil die Budgets verschieden sind.

### 4.10 „BKS“ statt „UCS“

Das Benutzerkoordinatensystem heißt in AutoCAD DE und Inventor DE **BKS**.
„UCS“ stehen zu lassen wäre die bequeme Entscheidung gewesen (der Befehl ist
ohnehin inaktiv), aber ein deutscher Anwender, der BKS gelernt hat, liest UCS
nicht als sein Werkzeug. Drei Buchstaben gegen drei Buchstaben — es kostet
nichts, es richtig zu machen.

### 4.11 Ein Begriff aus dem Auftrag, der hier nicht vorkommt

Der Auftrag nennt **Aufmaß**. Das ist ein Fertigungsbegriff (Materialzugabe
für die Nachbearbeitung), und diese App hat keine Stelle, an der er hingehört
— keine CAM-Seite, keine Toleranzen, keine Rohteildefinition. Er ist deshalb
in keinem Schlüssel gelandet. Ihn irgendwo unterzubringen, damit er vorkommt,
wäre die falsche Art von Vollständigkeit.

## 5. Was absichtlich englisch bleibt

Die Regel: **was gespeichert, geparst oder gemessen wird, wird nicht
übersetzt.** Eine übersetzte gespeicherte Zeichenkette ist eine Änderung am
Dateiformat.

| Was | Wo | Warum |
| --- | --- | --- |
| **`def`-Sätze der Arbeitselemente** | `part_model.dart:365/452/507` schreibt `'def': def` | Steht **in der `.ptp`**. Siehe §5.1 |
| Vorgabenamen: `Sketch7`, `Part3`, `Extrusion2` | `app_state.dart`, `part_model.dart` | Gehen in die Datei; `sketchNameExists('Sketch$n')` und `isPartName` prüfen sie auch noch |

| Kernel-Fehlertexte | `partKernel.lastError`, `f.computeError` | Kommen aus OCCT, durchgereicht als `{error}` |
| `work*MethodLabel` | `work_features.dart` | Englisches Domänenvokabular; in der Produktion ungelesen, nur von Tests geprüft |
| DXF/STEP-Schlüsselwörter, Layernamen im Dokument | Ex-/Importer | Fremdformat |
| `mm`, `°` | überall | SI-Symbole; DIN 1301 schreibt sie wie das Englische |
| `sin`, `cos`, `sqrt`, `pi` | Gleichungskurven-Dialog | Bezeichner des Parsers — sie werden so **eingegeben** |
| `DXF`, `STEP`, `ACAD`, `EOP` | Schaltflächen, Menüs | Formatnamen bzw. ein Kürzel, das schon im englischen UI steht |

| Logausgabe, `Log.i/w/e` | überall | Diagnose, nicht Oberfläche |

| `MaterialApp.title = 'Prototype'` | `main.dart` | Eigenname der Anwendung |

### 5.1 Der eine sichtbare Kompromiss

`WorkAxis.def` / `WorkPoint.def` / `WorkPlane.def` sind Sätze wie
`Through X Axis and Y Axis`, aus `WorkRef.label` zusammengebaut — **und sie
werden in die `.ptp` geschrieben.** Sie werden außerdem in einem Toast
angezeigt: `toast('${a.name}: ${a.def}')`.

Ergebnis: in der deutschen Oberfläche erscheint der Name auf Deutsch und der
Definitionssatz auf Englisch. Das ist ein Schönheitsfehler, und er bleibt
stehen. Die Alternative wäre, die Definition strukturiert zu speichern und
lokalisiert zu rendern — **das ist eine Änderung am Dateiformat** und damit
außerhalb dieser Session.

> **Für den Integrator.** Wenn das behoben werden soll: `def` als
> `{method, refA, refB}` ablegen statt als Satz, Satz beim Anzeigen bauen,
> alte Dateien mit vorhandenem `def`-String weiter lesen. Das ist eine
> Migration, keine Lokalisierung.

## 6. Zahlen

Anzeigeseitig deutsch, ansonsten unverändert. `lib/l10n/fmt.dart`:

* `Fmt.fixed/mm/deg` — Dezimalkomma auf Deutsch, Punkt auf Englisch.
  Angewendet auf Bemaßungsbeschriftungen im Ansichtsfenster, Scrub-Felder,
  das Versatzfeld der Arbeitsebene, die Parametertabelle, die Zahnrad-Kennwerte
  (Teilkreis / Kopf / Fuß), die Anordnungs-Koordinaten und die
  Verrundungs-Fehlermeldung.
* **Nicht angewendet** auf `PartFeature.ownSig()`, die DXF/STEP-Schreiber,
  `bug_report.dart`, `log.dart`, `reality_scene.dart`, `gesture_trace.dart`.
  `ownSig()` ist der **Rebuild-Schlüssel**: ein Komma darin würde jeden
  zwischengespeicherten Volumenkörper in jedem vorhandenen Dokument
  ungültig machen. Eine Formatänderung im Kostüm einer Formatierung.
* `Fmt.num` nimmt **beide** Trennzeichen, in beiden Sprachen. Damit öffnet
  ein Dokument, das in der einen Sprache getippt wurde, in der anderen.

Der größte Teil des Codes war schon komma-tolerant: `replaceAll(',', '.')`
steht an einem Dutzend Stellen, und `params.dart` benutzt seit jeher `';'` als
Argumenttrenner, „weil `','` mit dem europäischen Dezimaltrenner kollidiert“.
Fünf HUD-Eingaben und ein Feld im Zahnrad-Dialog kannten nur den Punkt; sie
nehmen jetzt auch das Komma. **Das ist eine Erweiterung, keine Änderung:**
keine bisher gültige Eingabe wird ungültig, kein gespeicherter Wert bewegt
sich.

## 7. Die Tests

### 7.1 `l10n_completeness_test.dart` — beide Sprachen vollständig

Identische Schlüsselmengen in beide Richtungen, kein leerer Wert, gleiche
Platzhalter auf beiden Seiten, `@key`-Platzhalterblock und Meldung im
Einklang, beide erzeugten Klassen ladbar. **Ein Schlüssel, der nur auf einer
Seite steht, bricht den Build nicht** — gen-l10n fällt auf die Vorlage zurück,
und ein englischer Nutzer bekommt mitten in seiner Oberfläche einen deutschen
Satz. Genau das fängt dieser Test.

### 7.2 `l10n_length_test.dart` — die Layoutbremse

Das ist der Test, für den diese Session existiert. Zwei Tore, weil es zwei
verschiedene Fehler sind.

**Tor 1 — Zeichenbudget, pro Zeile, für Beschriftungen in Kästen fester
Breite.** Hergeleitet aus der Geometrie, nicht aus dem Geschmack: die
schmalste Ribbon-Schaltfläche ist `SizedBox(width: 62)`, ihre Beschriftung
rendert mit `ts(11.5)`, und die Schrift der App braucht bei dieser Größe im
Mittel gut 6 px je Zeichen. 62 px sind also zehn Zeichen und ein bisschen;
**12** ist die Stelle, an der eine Beschriftung sicher breiter ist als ihr
Kasten. Die `Text`-Widgets dort haben **kein** `maxLines` und **kein**
`overflow` — zu lang heißt nicht „…“, sondern *Umbruch* (das ganze Ribbon
wird höher) oder Überlauf (der gelb-schwarze Balken). Das Budget steht als
`x-maxChars` im ARB **neben der Zeichenkette, für die es gilt**, weil es zum
Widget gehört und nirgendwo sonst hin. 72 Schlüssel tragen eines.

Gemessen wird **pro Zeile**: zweizeilige Beschriftungen behalten ihr `\n`,
denn genau dieser Umbruch ist das Mittel, mit dem ein breiter Befehl in eine
schmale Spalte passt.

**Tor 2 — Wachstumsverhältnis, für jeden Schlüssel.** Lange Meldungen
umbrechen frei und brauchen kein Zeichenlimit, dürfen aber nicht aufgehen.

```
en ≤ 10  →  erlaubt = en × 2,0 + 4
en ≤ 20  →  erlaubt = en × 1,7 + 3
en ≤ 30  →  erlaubt = en × 1,5 + 3
sonst    →  erlaubt = en × 1,35 + 3
```

**Warum gestaffelt und nicht ein Faktor.** Ein fester Faktor ist die
naheliegende Regel und die falsche, weil Textexpansion nicht linear in der
Länge ist. Zu „Edit“ (4) gibt es kein vierbuchstabiges deutsches Wort —
„Bearbeiten“ *ist* das Wort, und kein Umformulieren macht es kürzer. Ein
Vierzig-Zeichen-Satz, der um die Hälfte wächst, wurde dagegen übersetzt statt
geschrieben. Die veröffentlichten Expansionstabellen (IBM, Microsoft) sagen
dasselbe: 100–200 % unter zehn Zeichen, gegen ~30 % bei Fließtext. Das
additive +3/+4 hält die kurzen Stufen gegen Rundung ehrlich.

Der Test prüft **auch sich selbst**: ein Sprung von 12 auf 34 Zeichen — der
Fall aus dem Auftrag — muss durchfallen, ein Sprung von 40 auf 90 ebenfalls,
und „Fertig“/„Abbrechen“/„Neu“/„Bearbeiten“/„Verschieben“ müssen durchgehen.
Ein Tor, das nur „zu lang“ erkennt und dabei richtige kurze Übersetzungen
verwirft, wird nach dem dritten falschen Alarm abgeschaltet.

**Er hat beim ersten Lauf 31 Schlüssel gefunden.** Zehn davon waren echt zu
lang und wurden **umgeschrieben, nicht durchgewinkt** — „Die Skizzenpunkte
antippen, auf die die Bohrungen kommen.“ (57) wurde zu „Skizzenpunkte für die
Bohrungen antippen.“ (40), was auch das bessere Deutsch ist. Die übrigen 21
waren kurze Wörter, deren deutsche Entsprechung schlicht länger ist — die
haben das Tor korrigiert, nicht die Übersetzung.

### 7.3 `l10n_toggle_test.dart` — schalten, merken, nicht neu starten

15 Prüfungen: Deutsch als Vorgabe, Umschalten benachrichtigt genau einmal, ein
Umschalten auf die laufende Sprache benachrichtigt **niemanden** (sonst baut
die App ohne Grund neu), eine unbekannte Sprache wird ignoriert statt
geworfen, die Wahl steht in der Datei und wird nach einem simulierten Neustart

### 7.3a Der Fund, den kein Scanner hatte

Beim Durchsehen der Testprotokolle stand in einer Logzeile
`ui: notice: Select the third point.` — eine **englische** Meldung, lange
nachdem ich „fertig“ war.

`work_features.dart` hält drei Funktionen — `workAxisPrompt`,
`workPointPrompt`, `workPlanePrompt` — und 55 `WorkAttempt.no(…)`-Absagen,
zusammen **82 Sätze**, die der Nutzer während jedes Arbeitselement-Befehls
liest. Kein einziger stand in einer Argumentposition: es sind schlichte
`return '…';` in switch-Anweisungen. Weder der `toast(`-Scan noch der
Argument-Scan noch die Ratsche konnten sie sehen.

Sie sind jetzt übersetzt (`_t.…`, gelesen aus `L.current`, gleiche Naht wie
`native_browser.dart`). Was dabei **nicht** übersetzt wurde und warum:

* die `def`-Sätze (`Through ${a.label} and ${b.label}`, `Intersection of …`,
  `Tangent to …`) — sie gehen in die `.ptp`, siehe §5.1;
* `workAxisMethodLabel` / `workPointMethodLabel` / `workPlaneMethodLabel` —
  das englische Domänenvokabular. Sie werden in der Produktion nicht mehr
  gelesen (das Ribbon nimmt die ARB-Schlüssel); nur Tests prüfen sie noch.

**Die Lehre, ehrlich notiert:** eine Zeichenkette findet man zuverlässig
dort, wo sie *übergeben* wird, und unzuverlässig dort, wo sie *entsteht*.
Gefunden hat sie am Ende eine Logzeile in einem Testprotokoll, nicht mein
Werkzeug.

Und ein zweiter, kleinerer: mein erster Konvertierer hat Apostrophe in
Kommentaren (`Inventor's`) für Zeichenkettenanfänge gehalten und dadurch
halbe Dateien als „Zeichenkette“ gelesen. Der zweite maskiert Kommentare
offsettreu, bevor er sucht. Ein Regex ist kein Parser, und in einer Datei mit
600 Zeilen Prosa in Kommentaren merkt man das.

### 7.4 Die Ribbon-Breite — was kein Wortlimit sehen kann

Das Zeichenbudget prüft **eine** Beschriftung. Es sieht die Summe nicht: elf
Gruppen, jede zwei Zeichen breiter, ergeben ein Ribbon, das der Nutzer
weiterschieben muss. Das weiß nur ein gelayoutetes Widget, also misst
`l10n_toggle_test` das Ribbon in beiden Sprachen und vergleicht:

```
deutsch 1759 px   englisch 1681 px   +4,7 %
```

Grenze ist ein Fünftel. Das Ribbon ist absichtlich ein horizontaler Scroller —
zu breit ist also kein Absturz, sondern eine Wischgeste. Ein Fünftel ist eine
Wischgeste; die Hälfte mehr ist ein Befehl, den der Nutzer suchen muss.

**Gefunden hat das ein bestehender Test, nicht ich.**
`m50_ribbon_slimming_test` pumpt das Ribbon auf 1600 px und tippt die
Gruppentitel an. Beide Sprachen überlaufen 1600 px schon vorher; die deutschen
78 px haben „Ändern“ von knapp innerhalb auf x = 1599,8 geschoben — also
außerhalb. Der Test tippte auf ein Widget, das nicht mehr zu treffen war. Das
ist ein Testartefakt und kein Defekt (auf dem Gerät wischt man), deshalb
scrollt `openOverflow` jetzt erst zur Gruppe. Die Zahl oben ist der Grund,
warum das die richtige Antwort ist und nicht das Zurechtbiegen einer
Übersetzung.

### 7.4a Was die Ratsche gefunden hat, als sie breiter wurde

Die erste Fassung der Ratsche sah nur **benannte** Argumente und `Text(…)`.
Damit hat sie rund **180 Zeichenketten übersehen** — die Element-Dialoge geben
ihre Beschriftungen positional weiter:

```dart
panelRow('Start A', …)                 // erstes Positionsargument
('coincident', 'Coincident')           // Tupel in einer Liste
_modCol(['trim', …], ['Trim', …])      // parallele Listen
```

Nach dem Verbreitern (jede prosa-artige Zeichenkette, Kommentare maskiert)
kamen noch zwei ganze Gruppen ans Licht, die ich sonst ausgeliefert hätte:

* **die Validierer.** Rund 40 Sätze, die als `String?` aus den Vorschau- und
  Commit-Prüfungen zurückkommen — „Radius muss größer als 0 sein.“,
  „Winkel A + B dürfen 360 Grad nicht überschreiten.“ Sie gehen nie durch
  `toast()` und stehen in keinem Argumentnamen; sie erscheinen als die rote
  Zeile am Fuß eines Dialogs, also genau dort, wo ein Nutzer am längsten
  liest.
* **Ternäre Zweige.** `toast(a ? 'Nothing to undo.' : 'Nothing to redo.')` —
  der Schlüssel existierte längst, aber der erste Konvertierer nahm nur
  `toast('…')` mit reinem Zeichenketten-Argument.

**Das ist die Lehre dieser Session, und sie ist unbequem:** ein Werkzeug
findet, wonach es sucht. Drei Durchgänge mit drei verschiedenen Heuristiken
haben drei verschiedene Pfützen gefunden, und die letzte war nicht die
kleinste. Deshalb ist die Ratsche jetzt so breit wie möglich und arbeitet
gegen eine **begründete Ausnahmeliste** statt gegen eine enge Suche.

### 7.5 `l10n_no_hardcoded_test.dart` — die Ratsche

Ein Quellscan über die Widget-Schicht: erstes Positionsargument von `Text(…)`
und die Argumente `label:`/`title:`/`message:`/`tooltip:`/`hint:`. Absichtlich
eng gefasst, damit SVG-Nutzlasten, JSON-Schlüssel, DXF-Schlüsselwörter,
Logmarken und Symbolnamen gar nicht erst in sein Blickfeld geraten. Die
Ausnahmeliste hat genau einen Eintrag (`MaterialApp.title`), jeder Eintrag
braucht eine Begründung, und ein zweiter Test prüft, dass die Ausnahmen nicht
veralten.

Damit kann die nächste Funktion keine feste Beschriftung mehr einschmuggeln.

Die Ausnahmeliste hat **105 Einträge in acht Dateien**, gruppiert mit je einer
Begründung: gespeicherte Namen und `def`-Sätze, `WorkRef.label`-Werte, das
DXF-Schlüsselwort `Defpoints`, ein Schriftname, eine Regex und die Klammern um
einen bereits lokalisierten Wert. Ein zweiter Test prüft, dass keine Ausnahme
ihre Zeichenkette überlebt: verschwindet das Literal aus dem Baum, fällt die
Ausnahme auf.

Kommentare werden vorher **offsettreu maskiert** — sonst öffnet ein Apostroph
in `Inventor's` eine Schein-Zeichenkette, die den halben Rest der Datei
verschluckt (das ist meinem ersten Konvertierer genau so passiert). Die
Argumentlisten von `Log.*`, `assert` und `debugPrint` werden ebenfalls
maskiert: Logausgabe ist Diagnose, bleibt englisch, und ohne diese Maske
bestünde die Ausnahmeliste aus zweihundert Logzeilen.
